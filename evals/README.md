# 内容质量评测

现有测试只能说明流程图**能生成、能交互**，说明不了**讲得对不对**。这里用一个公开的开源游戏仓库出题，写好答案键，给 skill 产出的 `flow.json` 自动打分。改 SKILL.md、追踪方法、数据结构之后，重新跑一遍，就能看出变好还是变差。

## 题目

两个项目，版本都固定在 `sources.json`：

- [Shattered Pixel Dungeon](https://github.com/00-Evan/shattered-pixel-dungeon) v4.0.2（commit `57a4e06`，约 1300 个 Java 文件）：逻辑和数值都在代码里。
- [EGamePlay](https://github.com/m969/EGamePlay)（commit `e0fccfe`，MIT）：Unity C# 战斗框架，公式在代码，数值在 Excel 表和 Unity `.asset` 技能配置里，代码有 UTF-8 也有 GBK。更接近「客户端 + 配置表」的真实项目，而且有配置写了、代码没接上的地方。

| 题目 | 问题 | 陷阱（容易写错的地方） |
|---|---|---|
| `spd-melee-damage` | 近战攻击一次，最后打到怪身上的伤害是怎么算出来的？ | 护甲值一开始就掷出，但要等倍率和 defenseProc 之后才减；易伤 ×1.33 在减护甲之后 |
| `spd-hit-check` | 攻击时是怎么判定命中还是闪避的？ | 先判无限闪避，所以必闪压过必中；必闪时不掷骰 |
| `spd-loot-drop` | 怪物死了以后，掉不掉东西、掉什么是怎么决定的？ | 等级超限时连财富戒指额外掉落也没有；被偷、没掷中都不影响财富戒指判定 |
| `eg-damage-pipeline` | 这个项目里，一次伤害是怎么算出来、最后扣到血上的？ | 代码按普攻 / 技能 / Buff 分三支，但只有技能来源会被赋值，另两支走不到；Buff 分支掷了暴击却不乘 1.5 |
| `eg-fireball-falloff` | 火弹（1005）打中多个目标时，每个目标会受到多少伤害？ | Excel 描述和技能配置都写了「每个目标减 20%，最低 40%」，但算衰减的函数没有任何调用，每个目标都是 500 |
| `eg-burn-dot` | 血红激光炮（1004）挂上的灼烧，每跳扣多少血、多久跳一次、持续多久、能暴击吗？ | 灼烧配置里只有「伤害取值」这个名字，260 是挂 Buff 时字符串替换进去的；每一跳按技能伤害处理，不走 Buff 分支 |

每道题的 `cases/<id>.json` 里写着答案键和源码出处（文件和行号），`gold/<id>.flow.json` 是满分的参考答案，也可以当作好答案的样子来看。

## 怎么跑一次

1. 拉源码（会放到 `evals/.sources/`，不进 Git）：

   ```text
   python evals/fetch_sources.py
   ```

2. 在 Codex 里装好要测的 skill 版本，开一个**新会话**，原样发（目录用上一步打印的「give the skill this directory」，问题用题目表里的原话）：

   ```text
   使用 $project-handbook。

   这是代码目录：<目录>
   输出目录用：<任意空目录>\<题目 id>

   近战攻击一次，最后打到怪身上的伤害是怎么算出来的？
   ```

   每道题单独开一个新会话。不要把 `evals/` 目录给 agent，它不能看到答案键。

3. 把输出目录里的 `flow.json` 复制到 `evals/runs/<题目 id>/<日期>-<说明>.flow.json`，比如 `evals/runs/spd-loot-drop/2026-11-03-v1.5.0.flow.json`。

4. 打分：

   ```text
   python evals/score_flow.py --runs evals/runs
   python evals/score_flow.py evals/cases/spd-loot-drop.json evals/runs/spd-loot-drop/2026-11-03-v1.5.0.flow.json
   ```

   第二条会列出每一项没过的检查，`TRAP` 开头的是陷阱。

## 基线

Codex 6.1 Sol · GPT 高。1.5.0 只跑了破碎地牢的三道题；2.0.0 六道题各跑两次（a、b），每次都是新会话。输出在 `runs/<题目 id>/2026-11-04-codex-<版本>.flow.json`，`locator` 已改成仓库内的相对路径。

| 题目 | 1.5.0 | 2.0.0-a | 2.0.0-b | 陷阱 (a / b) |
|---|---|---|---|---|
| spd-melee-damage | 100 | 100 | 93.3 | 3/3 · 3/3 |
| spd-hit-check | 100 | 93.3 | 96.7 | 1/2 · 2/2 |
| spd-loot-drop | 94.5 | 91.0 | 93.5 | 3/3 · 3/3 |
| eg-damage-pipeline | — | 95.7 | 90.7 | 3/3 · 3/3 |
| eg-fireball-falloff | — | 100 | 100 | 2/2 · 2/2 |
| eg-burn-dot | — | 96.2 | 100 | 2/2 · 2/2 |

12 份 2.0.0 输出都对照源码人工核对过，陷阱题的结论全部正确，没有编造。扣分分两类。

答案里真实存在的问题：

- eg-damage-pipeline 两次都把「行动前触发」画在伤害计算之后。源码 `ActionSystem.ExecuteAction` 是先触发再计算，这个错误两次都出现。b 还把「能否暴击」写在说明里，没有画成判断节点。b 对普攻和 Buff 分支走不到这一点说得比较保守：「仓库里没有搜到创建调用」，没有直接下结论。
- spd-hit-check b 把掷骰画在无限闪避 / 无限命中检查之前，源码 `Char.hit` 是先检查再掷骰。最终判定结果不受影响，但流程顺序是错的。
- spd-loot-drop 三次都没提药水和卷轴可能变成异种版本。a 把掉落率公式节点画在掷骰之后，另一部分说明物品的节点也没有连到主流程上。
- spd-melee-damage b 没写狂怒 ×1.5、虚弱 ×0.67 这两个具体倍率，只写了状态名。
- eg-burn-dot a 把「间隔到了」和「每跳伤害」写在同一个节点里，没有分开。

打分规则的局限（答案是对的，分数偏低）：

- spd-hit-check a 用一个多分支节点按顺序列出「先：无限闪避 / 否则：无限命中 / 否则：随机对抗」，顺序是对的，但现在的打分规则看不出多分支节点内部的先后，所以陷阱只算过了 1/2。

2.0.0 新增的结构用得不均匀：12 份里有 7 份用了多分支节点；11 份给节点标了出处，其中 7 份每个节点都标了，spd-hit-check b 一个都没标。没标的节点会退回整张图的出处。这次跑的过程中还观察到：

- 掉落题 b 先输出了一版，然后自己复查修正，再输出到新目录 `revised/`，因为 build 不允许覆盖已有目录。修正后从 84.0 涨到 93.5。
- 有两道题 Codex 把输出放进了指定目录下的子目录（`handbook/`），因为它先把 `flow.json` 写进了指定目录，这个目录就不再是空的。输出目录约定需要说得更明确。
- 1.5.0 那轮掉落页面上追问「dropBonus 由哪几项组成」，检索只取回了文件头和 import 行。之后的检索改进已经修好了这个问题，见下一节。

## 页面追问的源码检索

追问时如果流程图里的说明不够，模型会请求一次关键词检索，由本地服务在授权目录里查找。`retrieval/spd.json` 有 17 道检索题，每题写的是模型会发出的检索词，以及结果里必须出现的文件和行号。

```text
python evals/score_retrieval.py <破碎地牢的目录>
python evals/score_retrieval.py <EGamePlay 的目录> evals/retrieval/egameplay.json
```

| 版本 | 破碎地牢（17 题） | EGamePlay（8 题） |
|---|---|---|
| 旧版（只按文件名挑 400 个文件读、每个文件取命中最多的一行） | 9 | 4 |
| 2.0（读全部文件、忽略 import、罕见词加权、定义加分、读 Excel 和 `.asset`） | 17，其中 13 题排第 1 | 8，其中 6 题排第 1 |

EGamePlay 的检索题专门覆盖：GBK 编码的代码、`.asset` 里 `\u` 转义的中文、Excel 的行。

旧版漏掉的大多是两种情况：真正的代码文件根本没被读到，或者被读到了却只截出 import 行。基线里「dropBonus 由哪几项组成」答不出来，就是这个原因。

## 分数怎么算

满分 100：

| 项 | 权重 | 看什么 |
|---|---|---|
| concepts | 40 | 答案键里的每个步骤，图里有没有节点讲到 |
| order | 30 | 步骤之间的先后顺序；判断节点的两条出口各自通到哪里 |
| decisions | 10 | 该画成是/否判断的地方是不是判断节点 |
| constants | 10 | 关键数值（倍率、次数）有没有出现 |
| evidence | 10 | 来源有没有写到对的文件；有没有一个完整的数值例子 |

## 局限

- 匹配靠关键词。答案键里同时列了代码名和常见中文说法，但换一种说法还是可能漏判；"不扣血"这种否定句也会被当成提到了"扣血"。分数异常时，打开报告看具体是哪一项，再对照流程图人工确认。
- 打分只看内容，不看排版。连线是否遮挡、能不能缩放，由 `tests/` 里的浏览器测试负责。
- 一道题跑一次的分数会有波动。比较两个版本时，每道题至少各跑 2 次，看平均分和陷阱通过数。
- 还没有「客户端 + 服务端」两份代码一起读的题，也没有 Lua 项目。

## 加一道题

1. 在固定版本的源码里读清楚逻辑，写 `cases/<id>.json`：`concepts` 的 `any` 同时写代码名和中文说法；陷阱写进 `order` 并标 `"trap": true`；`evidence` 写文件和行号。
2. 写 `gold/<id>.flow.json`，确认 `python evals/score_flow.py` 给它 100 分。
3. 在 `tests/test_eval_scoring.py` 里补一个"看起来对、其实错"的变体，确认陷阱能把它扣下来。
