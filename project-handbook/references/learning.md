# 新人问题讲解手册

适用于用户提供客户端、服务端、文档目录，并提出“奖励这块怎么做的”“我想了解登录”“这套计算怎么走”等模糊问题。默认目标不是一张孤立流程图，也不是全项目百科，而是一条由浅入深、可复述的解释路线。

## 1. 理解问题，不把澄清负担交回新人

先只读浏览目录、入口、模块说明和相关文档，再记录：原问题、你的理解、涵盖范围、不涵盖范围。通常默认解释职责、入口、主流程、关键分支、完整例子、修改与排查位置。不要要求新人先说出函数或模块名。

只有两种理解会导致明显不同的分析范围时，问一个短问题。例如“奖励”可能指发放链路，也可能指全局经济投放；否则主动采用合理范围并在页面展示解释。用户只说“了解项目”时，先给全局骨架，再选一个有证据的代表性端到端流程，明确其他模块尚未深入。

## 2. 定向追踪，而不是抽样完就宣布理解

目录导入是发现工具，不是语义分析器。不得将排名靠前的文件当成真实入口、调用顺序或完整答案。分析由调用此 skill 的 agent 完成，渲染器只检验并展示已审阅内容。

围绕主题逐条追踪并在私有分析记录中保存：

| 起点 | 查什么 | 如何确认 |
|---|---|---|
| 界面入口 | 按钮、路由、事件、任务触发器 | 真实事件绑定与调用位置 |
| 请求协议 | 请求名、参数、返回码 | 发送处与接收注册表互相对应 |
| 服务端处理 | 校验、分支、业务调用 | 函数体和实际引用，不只看名字 |
| 配置 | 读取键、表、字段、默认值 | 引用链与实际单元格/配置值 |
| 结果 | 状态变更、存储、消息回传 | 写入函数、返回结构与展示处理 |
| 异常 | 提前退出、失败回滚、重试 | 独立分支或测试/日志证据 |

每条追踪记录写“起点定位 → 目标定位 → 关系类型 → 已核对/资料声明/缺口”。只按证据继续跟随相关调用和引用，不扫描所有文件正文。对反射、生成代码或运行期注册，找不到映射就保留缺口；“搜索不到”不等于“不存在”。

原始目录只读，不运行导入的脚本、宏、构建和启动命令。不要输出密钥。XLSX 需要实际表名和单元格值；仅文件名与维度不构成业务证据。源码与旧文档冲突时，以来源类型和时间分别说明；静态代码存在不等于现网部署或实测。

## 3. 六层阅读契约

1. **先看答案**：通俗短结论，回答原问题；缺口不淹没答案。
2. **看懂框架**：通常 3–8 个职责节点，用明确关系解释本问题的位置。
3. **走完流程**：每步写谁负责、输入、做什么、输出；细节折叠。
4. **跟着例子走**：初始条件、每一步的中间值/状态、最终结果；回链到原步骤。
5. **术语与细节**：业务词、代码名、别名对照，避免先抛函数名。
6. **回到实际工作**：改哪里、查哪里、验证什么；列出已查到、尚缺、下一步。

默认至少一个完整例子；证据允许时提供正常、边界、异常三个例子。提前失败的例子必须说明跳过哪些步骤，不补造成功结果。没有内层公式就展示到可确认的位置，不伪造计算器。

## 4. Manifest

在现有 knowledge manifest 中增加 `learning`，完整可运行样例见 `assets/learning.example.json`。保留现有 `sources`、`systems` 字段以兼容站点生成。

- `question`, `interpretation`, `answer`：非空文本。
- `scope`, `excluded`：字符串数组；`status`, `sources` 描述总结的证据。
- `diagram.type`：`architecture|workflow|sequence|lifecycle|calculation`。
- `diagram.nodes[]`：`id,title,body,status,sources`。
- `diagram.edges[]`：`from,to,label,status,sources`，仅表示作者核对/声明的有向关系。节点位置与阅读顺序不是新增的运行关系。
- `steps[]`：`id,node,title,owner,input,action,output,status,sources`，可选纯文本 `details`。步骤 `node` 必须引用框架节点。
- `examples[]`：`id,title,kind,input,trace,result,provenance,status,sources`。`kind=normal|boundary|exception`，`trace[]` 含 `step,value,sources`。
- `provenance=illustrative` 表示演示推演，不得标 `verified`；`observed` 必须引用测试或日志记录，不是单纯阅读代码的结论。
- `glossary[]`：`term,aliases[],meaning`。
- `actions[]`：`title,body,step,sources`。
- `coverage[]`：`area,checked,missing,next`，不得省略未覆盖范围。

所有正文均为纯文本，由渲染器转义。ID 使用小写字母、数字、连字符，字母开头，最多 45 字符。同类 ID 不重复，来源、节点和步骤引用必须存在。已核对的结论必须有来源，校验器不能代替人工判断证据是否真的支持结论。

图型选择：职责用 architecture、交互时间顺序用 sequence、步骤分支用 workflow、状态变化用 lifecycle、输入/规则/输出计算用 calculation。不要为了使用某种图而补造节点、关系或数值。

## 5. 构建、交付与验收

```text
python scripts/build_knowledge.py assets/learning.example.json new-handbook
python scripts/verify_handbook.py new-handbook
python scripts/verify_handbook.py new-handbook/handbook.html
```

默认交付 `handbook.html`，样式、脚本和来源摘录均内嵌，双击可读，不请求网络、不调用模型、不读取凭据。原有 `site/` 保留兼容与可选在线问答。单文件没有目录上传控件：目录由 agent 读取，页面是已完成的讲解成果。不要把“可离线阅读”说成“浏览器会自动理解代码目录”。

验收：原问题是否回答；框架与步骤互相对应；导读前进/后退/退出；例子回到步骤；证据展开并返回；术语别名搜索；无匹配状态；文件移动到另一目录仍可读；手机宽度、键盘、深链接、主题切换；关闭网络仍能读完整答案。

构建新目录，保留上版，不覆盖用户文件。报告真实测试范围，合成案例通过不等于真实项目已分析；真实供应商连通性也不能替代答案事实核验。
